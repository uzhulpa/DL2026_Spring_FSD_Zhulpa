# Часть 1. Проектирование и анализ

Цель этой части — зафиксировать понимание задачи, спроектировать структуру приложения и проработать детали до этапа реализации. Ниже описано проектное решение, в соответствии с которым было реализовано текущее приложение.

---

## 1.1. Пользовательские сценарии

**User story 1.** Как пользователь, я хочу ввести название города и увидеть актуальную погоду в понятном виде вместе с юмористическим мемом, соответствующим условиям, чтобы быстро оценить погоду и поднять настроение.

**User story 2.** Как пользователь, я хочу указать широту и долготу (или воспользоваться определением места по IP), чтобы получить прогноз для точки на карте или для своего текущего подключения без ручного ввода города.

**User story 3.** Как пользователь, я хочу открыть одну страницу в браузере и работать с интерфейсом без отдельной авторизации, чтобы сразу воспользоваться сервисом в учебной или демонстрационной среде.

---

## 1.2. Функциональные требования

### Обязательные

**Фронтенд**

- Форма или панель выбора режима: поиск по городу, ввод координат, запрос по IP.
- Валидация ввода города и координат на стороне клиента (минимальная длина, диапазоны широты/долготы, запрет явно опасных символов).
- Отображение блока с местоположением, числовыми и текстовыми параметрами погоды и блока с мемом (текст и/или изображение по URL).
- Загрузка данных через `fetch` к собственному бэкенду; при необходимости — обращение к публичному сервису геолокации по IP из браузера.
- Адаптивная вёрстка (SCSS, медиазапросы).

**Бэкенд**

- HTTP API для получения агрегированного ответа: место + погода + мем.
- Определение координат: геокодирование названия города (внешний API), прямое использование переданных `lat`/`lon`, либо определение по IP запроса (с учётом локальной разработки и приватных диапазонов).
- Запрос текущей погоды по координатам у погодного провайдера.
- Подбор мема из базы по коду погоды (соответствие коду OpenWeather); при отсутствии записи — запасной (дефолтный) мем.
- Раздача статических файлов фронтенда тем же сервером, что и API.
- Проверка работоспособности сервиса (health-check).

### Опциональные / расширения

- Наполнение справочников категорий погоды и мемов сидером при развёртывании.
- Учёт просмотров мемов в модели данных (поле в БД; дальнейшее использование в аналитике не входит в минимальный объём).
- Контейнеризация (Docker Compose) для совместного запуска приложения и PostgreSQL.

## 1.3. Проектирование API

Авторизация и токены для клиента **не используются**: приложение рассчитано на открытый доступ в рамках учебного проекта. Секретный ключ погодного API хранится только на сервере в переменных окружения.

### `GET /api/health`

**Назначение:** проверка доступности сервера.

**Параметры:** нет.

**Успешный ответ:** `200 OK`, тело JSON:

```json
{
  "status": "OK",
  "message": "Сервер работает",
  "timestamp": "2026-03-22T12:00:00.000Z"
}
```

### `GET /api/weather`

**Назначение:** получить сводку по местоположению, погоде и связанному мему.

**Параметры запроса (query, взаимоисключающие сценарии комбинируются по приоритету на бэкенде):**

| Параметр | Описание |
|----------|----------|
| `city` | Название города; бэкенд получает координаты через геокодирование. |
| `lat`, `lon` | Широта и долгота (числа). |
| `ip` | Явное указание IP для геолокации (опционально). |
| *(нет параметров)* | Используется IP клиента из запроса для определения координат. |

**Успешный ответ:** `200 OK`, JSON:

```json
{
  "success": true,
  "location": {
    "method": "строка-описание способа определения места",
    "city": "строка",
    "country": "строка",
    "coordinates": { "lat": 0, "lon": 0 }
  },
  "weather": {
    "temp_celsius": 0,
    "feels_like": 0,
    "pressure": 0,
    "humidity": 0,
    "visibility": 0,
    "wind_speed": 0,
    "wind_direction": 0,
    "clouds": 0,
    "weather_code": 0,
    "weather_main": "строка",
    "weather_description": "строка",
    "weather_icon": "строка",
    "sunrise": "строка",
    "sunset": "строка",
    "sunrise_timestamp": 0,
    "sunset_timestamp": 0,
    "city_name": "строка",
    "country": "строка"
  },
  "meme": {
    "image_url": "строка или null",
    "text_content": "строка",
    "id": 0
  }
}
```

**Типовые ошибки:**

| Код | Ситуация |
|-----|----------|
| `400` | Некорректные координаты или ошибки геокодирования по смыслу запроса. |
| `404` | Город не найден или не удалось определить местоположение. |
| `502` | Сбой внешнего погодного API или связанного сервиса. |
| `500` | Прочая внутренняя ошибка. |

Тела ошибок — JSON с полями `error` и `message` (человекочитаемое пояснение).

## 1.4. Модель данных

Хранение — **реляционная СУБД PostgreSQL**, доступ через **Sequelize**.

### Сущность «категория погоды» (`weather_categories`)

Справочник соответствий кода погоды OpenWeather и метаданных для UI/логики.

| Поле | Тип | Ограничения |
|------|-----|-------------|
| `id` | INTEGER | PK, автоинкремент |
| `name` | VARCHAR(50) | NOT NULL |
| `weather_code` | SMALLINT | NOT NULL, UNIQUE (код условия OpenWeather) |
| `description` | VARCHAR(100) | NULL |
| `icon_day` | VARCHAR(3) | NOT NULL |
| `icon_night` | VARCHAR(3) | NOT NULL |

### Сущность «мем» (`memes`)

| Поле | Тип | Ограничения |
|------|-----|-------------|
| `id` | INTEGER | PK, автоинкремент |
| `weather_category_code` | SMALLINT | NOT NULL, FK → `weather_categories.weather_code` |
| `image_url` | TEXT | NULL |
| `text_content` | TEXT | NULL |
| `views` | INTEGER | NOT NULL, по умолчанию `0` |

**Связь:** одна категория погоды — много мемов; выбор мема для ответа API — случайная запись среди мемов с нужным `weather_category_code`.

### JSON-схема связей (логическая)

```json
{
  "WeatherCategory": {
    "id": "integer",
    "name": "string",
    "weather_code": "integer",
    "description": "string | null",
    "icon_day": "string",
    "icon_night": "string"
  },
  "Meme": {
    "id": "integer",
    "weather_category_code": "integer",
    "image_url": "string | null",
    "text_content": "string | null",
    "views": "integer"
  },
  "relations": [
    "Meme.weather_category_code -> WeatherCategory.weather_code"
  ]
}
```

Схема таблиц создаётся и синхронизируется через Sequelize (`sync`) при старте приложения; начальное наполнение — отдельным сидером.

## 1.5. Ключевые технические решения

**Фронтенд:** без SPA-фреймворка — статическая разметка и модульный JS, стили на **SCSS** с последующей компиляцией в CSS. Это упрощает вводный проект, уменьшает порог входа и достаточно для формы запросов и отображения карточек погоды и мема.

**Бэкенд:** **Node.js** с **Express** (маршрутизация, JSON, статика). Асинхронные вызовы внешних HTTP API — **Axios**. Конфигурация — **dotenv** для локальной и контейнерной среды.

**База данных:** **PostgreSQL** как надёжная реляционная СУБД, удобная для справочников и связей «код погоды — набор мемов». **Sequelize** выбран как ORM с поддержкой миграций/синхронизации моделей и декларативного описания связей.

**Внешние API**

- **OpenWeather (Current Weather Data)** — текущая погода по координатам; ключ только на сервере.
- **Геокодирование** — отдельный вызов к API OpenWeather для преобразования города в координаты (единый ключ и экосистема провайдера).
- **Геолокация по IP** — на бэкенде через выбранный сервис по IP клиента; на фронте при сценарии «по IP» дополнительно может использоваться публичный **ip-api.com** для получения координат в браузере с последующим запросом к своему `/api/weather` по `lat`/`lon`.

**Развёртывание:** один процесс Node раздаёт API и фронт; опционально **Docker Compose** поднимает PostgreSQL и приложение с согласованными переменными окружения.

Такой стек обеспечивает кроссплатформенность разработки (Windows/Linux), предсказуемую модель данных и чёткое разделение: клиент отвечает за UX и валидацию ввода, сервер — за секреты, интеграции и бизнес-логику подбора мема по коду погоды.
