# Работа с AI

Ниже зафиксирован опыт использования AI-инструментов при выполнении задания по проекту погоды и мемов (фронтенд, бэкенд, БД, Docker, документация).

---

## 3.1. Применённые инструменты и промпты

### Инструменты

Основной инструмент — **Cursor** (встроенный AI-ассистент в IDE: чат, правки по запросу, работа с репозиторием). Дополнительно в ходе работы теоретически могли использоваться **ChatGPT** или **GitHub Copilot** для разовых вопросов, но централизованно сценарий «запрос → правка в проекте» шёл через Cursor.

### Примеры промптов и цели

**1. Геокодирование (генерация сервисного слоя)**

```
server/services/geocodingService.js

сделай класс сервиса

Создай функцию getCoordinatesByCity(city), которая делает GET запрос к OpenWeatherMap Geocoding API. Верни { lat, lon } или null если город не найден.

url для запроса:

http://api.openweathermap.org/geo/1.0/direct?q={city name}&limit={limit}&appid={API key}

api key получить из .env OPENWEATHER_API_KEY
```

*Назначение:* быстро получить каркас класса, Axios-запрос и разбор ответа API без ручного копирования документации OpenWeather.

**2. Геолокация по IP**

```
server/services/ipLocationService.js

сделай класс сервиса

Создай функции getCityByIp(ip), getCoordsByIp(ip). Используй бесплатный сервис ip-api.com/json/{ip}. в первой возвращай название города, во второй координаты lat lon
```

*Назначение:* вынести работу с ip-api в отдельный сервис с предсказуемым интерфейсом для контроллера погоды.

**3. Контроллер и единая точка входа API**

```
В weatherController объедини сценарии: city в query, lat/lon, ip и fallback на IP клиента.
Сначала получи координаты, потом погоду через OpenWeather, потом мем из БД по weather_code.
Верни JSON с location, weather, meme. Обработай 404/400/502.
```

*Назначение:* спроектировать поток запроса и снизить риск забыть ветку обработки; AI помогает выстроить структуру `try/catch` и коды ответов.

**4. Модели Sequelize и связь «категория — мемы»**

```
Опиши модели WeatherCategory и Meme: weather_code уникальный, у мема FK на weather_code,
hasMany/belongsTo. Добавь статический метод выбора случайного мема по коду погоды.
```

*Назначение:* ускорить объявление полей, типов и ассоциаций вместо чтения всей документации Sequelize с нуля.

**5. Docker и docker-compose**

```
Добавь в корень docker-compose: postgres 16 и Node-приложение.
Контекст сборки должен включать backend и frontend, потому что Express раздаёт ../frontend.
Переменные из backend/.env, в контейнере app переопредели DB_HOST на имя сервиса db.
```

*Назначение:* получить рабочий шаблон оркестрации без долгого перебора синтаксиса Compose.

**6. Документация**

```
В README опиши стек, установку зависимостей отдельно для frontend и backend,
настройку .env из .env.example, sass:build/sass:watch и запуск npm run dev.
```

*Назначение:* структурировать инструкцию под требования курса и не забыть шаги (SCSS, два терминала, health-check).

**7. Проектирование под уже существующий код**

```
В design.md опиши часть 1: user stories, требования, API, модель данных, стек —
как будто сначала был дизайн, потом реализация; сверь endpoint'ы с кодом.
```

*Назначение:* обратная инженерия в академическом формате с проверкой соответствия репозиторию.

**8. Отладка инфраструктуры**

```
Ошибка Docker: unable to get image postgres, pipe dockerDesktop — что проверить на Windows?
В логах postgres: FATAL role "root" does not exist каждые 5 секунд.
```

*Назначение:* сузить круг причин (демон Docker vs healthcheck `pg_isready` без `-U`) и не тратить время на неверные гипотезы про пароли.

## 3.2. Анализ эффективности

### Где AI оказался наиболее полезен

- **Шаблонный код сервисов** (геокодинг, IP, обёртка над OpenWeather): ускоряет старт, единообразный стиль Axios и обработки ошибок.
- **Docker / `.dockerignore` / структура compose:** экономит время на «первый подъём» стека, если подсказать контекст сборки (frontend + backend).
- **Документация (README, design):** быстро выстраивается оглавление и формулировки; остаётся вычитать и подставить факты из проекта.
- **Разбор типовых ошибок окружения** (Docker Desktop не запущен, pipe на Windows): даёт чеклист действий без лишней теории.

### Где ответы требовали серьёзной корректировки или были неверны

- **Healthcheck PostgreSQL:** изначально предложенный или упрощённый вариант `pg_isready -q` без указания пользователя на практике приводил к попыткам подключения от системного пользователя контейнера (`root`) и к повторяющимся `FATAL: role "root" does not exist`. Проблема обнаружена по **интервалу ошибок в логах** (совпадение с `interval` healthcheck) и по тексту ошибки PostgreSQL. Исправление — явно указать `-U` и базу через переменные образа (`POSTGRES_USER`, `POSTGRES_DB`).
- **Переменные окружения и пользователь БД:** AI легко предлагает «типичные» значения; если смешать соглашения MySQL (`root`) и PostgreSQL или пересоздать том с другими `POSTGRES_*`, получается рассинхрон. Нужна **проверка** против реального `docker compose config` и документации образа `postgres`.
- **Пути и `main` в `package.json`:** мелкие несоответствия (например, `server.js` vs `index.js`) AI не всегда ловит, если в промпте не указан актуальный файл входа — ловит **запуск** (`npm start`).

### Примеры по пунктам задания

| Ситуация | Что произошло |
|----------|----------------|
| **Ускорение** | Промпты к сервисам геокодинга и IP сократили время на чтение параметров API и написание `axios.get` с `params`. |
| **Ошибка AI / неточность** | Упрощённый healthcheck → шум в логах БД; выявлено сопоставлением периодичности с конфигом compose и знанием поведения `pg_isready`. |
| **Сознательный отказ** | Иногда отклонялись «лишние» рефакторинги или смена стека (например, введение ORM/фреймворка там, где по заданию достаточно простого стека), чтобы не раздувать diff и не усложнять сдачу. От части подсказок отказывались, если они **противоречили структуре репозитория** (`backend/` vs `server/`). |

## 3.3. Выводы и рекомендации

1. **AI — ускоритель черновика, а не замена запуска и тестов.** После генерации сервиса или compose-файла обязательны `npm start`, запрос к `/api/health`, `docker compose up` и просмотр логов; иначе легко пропустить ошибки в healthcheck, портах или переменных.

2. **Контекст в промпте снижает количество правок.** Имеет смысл указывать реальные пути (`backend/services/...`), имена переменных из `.env.example`, ограничения задания («без авторизации», «Express раздаёт frontend»). Тогда меньше расхождений с проектом.

3. **Документацию и дизайн-док AI может собрать из кода**, но ответственность за соответствие методичке и фактической реализации остаётся на авторе: нужно сверять endpoint'ы, поля моделей и сценарии с исходниками.

**Планы на будущие проекты:** использовать AI для разбора ошибок сборки/CI, генерации тестовых кейсов и черновиков README; не передавать секреты в промпты; хранить типовые удачные промпты в заметках команды.

**Совет коллегам, кто только начинает:** начинайте с малого запроса и одного файла; проверяйте каждый сгенерированный фрагмент в рантайме; если ответ «уверенный, но странный» — сверяйтесь с официальной документацией инструмента (Docker, Sequelize, провайдер API), а не только с текстом модели.
